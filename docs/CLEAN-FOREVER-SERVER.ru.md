# Чистый сервер Forever для фактической сборки клиента

5 ноября 2026 года пользователь подтвердил `Wow.exe` **1.60.1.70658** в
`E:\WoWForEver-work\experiments\Forever-client-v3\_forever_` и попросил начать
сервер заново, а наши дополнения поставить после проверки входа.

Используется чистая ветка `advocaite/TrinityCore:forever`, коммит
[`b4e7b940593f6402a822d4fbcdf31331d16f73b6`](https://github.com/advocaite/TrinityCore/commit/b4e7b940593f6402a822d4fbcdf31331d16f73b6).
В нём добавлена поддержка 70790, но для подтверждённого EXE 70658 выбирается
**realm.gamebuild = 70658**: переключение нумерации сообщений 70790 для него
не включается. Установка определяет версию EXE через Windows FileVersion,
сверяет EXE оригинала и тестовой копии по SHA-256 и проверяет их CASC build key.
Поле Version в `.build.info` само по себе не выбирает сетевой протокол.

Список «Бета-версия» в клиенте не является проверкой версии серверного ядра.
Upstream для этих клиентов по-прежнему требует RealmID 70 и ContentSetID 137.
В чистой базе остаётся одна запись realmlist: **Forever Clean, обычный мир,
70 / 8085 / ContentSetID 137 / SuperDistrictID 2**. После старта эта идентичность
проверяется повторно. Названия локализованных пунктов интерфейса клиента
этим инструментом не подменяются.

## Состав

- Новый Compose-проект `forever-clean`, отдельная сеть и новые MySQL/logs-тома.
- Четыре новые базы: auth, characters, world, hotfixes. Аккаунты и персонажи
  прежних проектов не импортируются.
- Официальная база Forever от 14 октября с проверкой SHA-256 архива;
  затем штатные SQL-обновления выбранного upstream-коммита.
- Новые dbc/gt/cameras/maps/vmaps, извлечённые штатными инструментами из
  текущего оригинала `E:\WoW_Forever`, product `wowf`. Старый DataDir сервера
  не монтируется и не копируется. Клиент монтируется только для чтения.
- Серверные бинарники собираются без наших patch/inject-advancement, модулей,
  overrides и экспериментального CLIENT_BUILD. Конфиги создаются из `.dist`.
- Отдельная сборка инструментов получает только read-only fallback CascLib
  для Linux. Уже собранные серверные бинарники не пересобираются; их SHA-256
  проверяется до и после установки инструментов.
- Сохраняется прежняя **TLS-идентичность**: сертификат и его ключ монтируются
  только для чтения. Multi продолжает доверять локальному серверу.
- Сайт нужен для создания новой учётной записи; его SOAP доступен только
  внутри сети. Игровые дополнения к ядру для этого не подключаются.

## Установка в WSL

Закройте обе копии игры и загрузчик оригинала. Запускайте из Ubuntu/WSL.
Нужны Docker Desktop, Python 3, Git, рабочий Windows interop для PowerShell
и минимум 15 ГиБ свободного места на файловой системе новой установки.
Полная компиляция и извлечение занимают время. Mmaps пока отключены.

```bash
cd ~/WoWForEver
git fetch origin codex/clean-forever-20261105 &&
clean_tools=$(mktemp -d "$HOME/WoWForEver-clean-tools.XXXXXX") &&
git worktree add --detach "$clean_tools" FETCH_HEAD &&
python3 "$clean_tools/scripts/clean-forever-server.py" install \
  --client /mnt/e/WoW_Forever \
  --test-client /mnt/e/WoWForEver-work/experiments/Forever-client-v3/_forever_ \
  --client-build 70658 --jobs 2
```

`--client-build 70658` сверяется с наблюдаемой версией EXE, если Windows
interop доступен. Несовпадение вызывает остановку; auth build_info не
подделывается, выбранная сборка должна существовать в штатной схеме upstream.

Первый запуск создаёт **новую** папку `~/WoWForEver-clean` с закрытыми правами.
Если папка уже существует без корректного state.json, её файлы не принимаются
и не удаляются. Повторный install использует checkpoint; готовые базы заново
не сбрасываются. state.json, compose.private.json и конфиги содержат новые
локальные пароли — их не нужно присылать в чат или Git.

Последовательность: сборка → новое извлечение → новый MySQL → одноразовый
импорт/обновления → один обычный realm → проверка готовности мира → остановка
прежних сервисов → публикация портов → проверка TLS с прежним CA.
Во время первых этапов прежние серверы продолжают работать. Прерывание ожидания
SQL-импорта не останавливает импортирующий контейнер; повторный install продолжит
ожидание. Не перезапускайте его во время первого импорта.

Успешный вывод: `CLEAN READY`. Сам по себе он ещё не подтверждает успешное
создание персонажа: это следующий тест на ПК пользователя.

### Если извлечение остановилось после `Ok, all done`

В первоначальном установщике проверка искала `.vmtree` только в корне vmaps.
Выбранный upstream сохраняет их в `vmaps/<mapid>/<mapid>.vmtree`, поэтому
успешный запуск assembler ошибочно считался неудачным. Исправленная проверка
ищет непустые payloads рекурсивно, включая локализованные DB2, и называет
отсутствующий тип данных при ошибке.

Получите свежий инструмент в отдельном worktree и продолжите имеющийся checkpoint:

```bash
cd ~/WoWForEver
git fetch origin codex/clean-forever-20261105 &&
clean_tools=$(mktemp -d "$HOME/WoWForEver-clean-tools.XXXXXX") &&
git worktree add --detach "$clean_tools" FETCH_HEAD &&
python3 "$clean_tools/scripts/clean-forever-server.py" install --client-build 70658 --jobs 2
```

В фазе `extracting` уже собранный Docker-образ не перекомпилируется: текущий
extract.sh монтируется только для чтения. Извлечение повторяется в новой папке;
предыдущая попытка остаётся для диагностики. Управляющий server.sh переключается
на этот worktree, который следует сохранить. Во время извлечения не запускайте
игру и загрузчик оригинала.

Сообщения `FILE_OFFLINE` означают, что extractor не смог прочитать конкретные
файлы локально; успешная структурная проверка не подтверждает наличие всех
ресурсов клиента. Они требуют отдельной проверки, если сервер сообщит о
недостающих данных или проблема входа сохранится.

### Если worldserver остановился на ArtifactKnowledgeMultiplier.txt

Подтверждённая ошибка: `LoadGameTables FATAL ERROR`, отсутствует
`gt/ArtifactKnowledgeMultiplier.txt`; контейнер завершается с кодом 139.
Это проверка обязательного файла, выполненная ядром после загрузки DB2.
Сообщения `hotfix_data references unknown DB2 store` сами по себе не являются
этой причиной завершения.

Свежий install проверяет все 14 GameTables из выбранного upstream перед
импортом и перед запуском worldserver. Для единственного отсутствующего
ArtifactKnowledgeMultiplier он читает FileDataID **1582086** из активного
ROOT оригинального `wowf`, пробует доступные локальные кодировки и проверяет
хеши BLTE/контента и табличную структуру. Клиент открывается только для чтения.
Если локально прочитать файл не удалось, разрешена закреплённая публичная
копия только при совпадении её MD5 с CKey **этого FileDataID текущего ROOT**;
дополнительно проверяется SHA-256 скачанных байтов. Чужая версия не принимается
только на основании имени файла или даты. Пустая заглушка и новые значения
множителей не генерируются. Игровые данные не помещаются в Git.

Для восстановления продолжите install свежим инструментом, как в блоке выше.
В фазе `initialized` сохраняются уже импортированные базы и извлечённые карты:
скрипт восстанавливает только отсутствующий файл и повторяет запуск сервера.
Перекомпиляция и повторный SQL-импорт не выполняются. Метаданные источника
и проверенные хеши сохраняются в `data/.clean-game-table-repair.json`.
Поскольку extractor создаёт файлы от root, запись выполняет отдельный
контейнер уже собранного образа с единственным writable-монтом `data/gt`;
сеть отключена, клиент, базы и сертификаты в него не монтируются.
Если хеш текущего клиента не совпадёт или отсутствуют другие обязательные
таблицы, установка остановится с точным сообщением, сохранив прежние данные.

Если ранняя версия восстановления остановилась с `Conflicting local EKey prefixes`,
получите свежий инструмент и продолжите тот же `install`. Установленные CASC могут
содержать несколько физических записей одного 9-байтового EKey-префикса. Теперь
чтение восстановления перебирает все доступные расположения и принимает только
BLTE с совпадающим полным EKey, контрольными суммами блоков и ожидаемым CKey.
Короткие пустые записи и неподходящие байты не принимаются; если ни одна копия
не прошла проверку, выводится ошибка с EKey и числом кандидатов. Наличие дублей
в несвязанных файлах больше не останавливает чтение ENCODING/ROOT целиком.
Строгий запрет неоднозначных IDX для старых инструментов изменения CASC сохранён.
Индексы клиента при восстановлении не переписываются.

### Если ожидание готовности сопровождается потоком TC>

Подтверждённый случай: `worldserver` уже слушает 8085 внутри своего контейнера,
но `docker logs --tail 100 forever-clean-worldserver-1` содержит только `TC>`.
Это приглашения штатной интерактивной консоли при закрытом stdin в Docker.
Они вытесняли строку `worldserver-daemon ready` из tail, и прежняя проверка
продолжала ждать готовый сервер.

Текущий конфиг задаёт `Console.Enable = 0`; worldserver использует ограниченную
ротацию Docker-журнала. Python entrypoint монтируется read-only из текущего
инструмента, поэтому готовое ядро не требуется перекомпилировать. В фазе
`initialized` install обновляет Compose, один раз пересоздаёт worldserver
с этим конфигом и продолжает переключение; свежие базы и DataDir сохраняются.

Готовность больше не зависит от текста или хвоста старых журналов: проверяются
процесс, метки чистого ядра, TCP 8085 внутри именно его контейнера и единственный
realm 70 с фактическим build клиента, contentSetId 137 и снятым offline-флагом.
Только после этого выполняются переключение, запуск сайта/bnet и проверка TLS.

Если прежний install ещё печатает ожидание, прервите **его** через Ctrl+C
после подтверждённого `TCP 8085 OK`, затем получите свежий инструмент и
повторите install. Это прерывает клиентский процесс ожидания; контейнер мира
остаётся работающим до управляемого пересоздания обновлённым инструментом.

## Удаление прежнего сервера

После `CLEAN READY` выполните:

```bash
~/WoWForEver-clean/server.sh purge-old
```

Команда **удаляет** старые контейнеры, MySQL/logs-тома и сети только проектов
`forever` и `forever-refresh-70658`. Это стирает их аккаунты, персонажей и
изменения в world/hotfixes. Перед удалением проверяется готовность нового мира
и принадлежность ресурсов. Активные старые контейнеры и тома, используемые
другими контейнерами, не удаляются принудительно.
Исходники наших дополнений, клиентские папки, bind-каталоги, сертификаты,
старые архивы резервных копий и Docker-образы сохраняются; новый сервер их
игровые данные не использует. Общий `docker system prune` не применяется.

## Проверка без клиентских дополнений

После `CLEAN READY` установщик печатает готовую команду под заголовком
`WINDOWS CLIENT PREPARATION` и сохраняет копию помощника внутри
`.forever-multi` тестовой установки. Выполните эту команду в Windows PowerShell
после закрытия игры. Исходный помощник находится в
`tools/clean-server/Prepare-CleanClient.ps1`. Скрипт сам берёт
папку выбранной игры из сохранённых настроек Multi, либо принимает явный
`-GameDirectory`. Оригинал задаётся `-OriginalDirectory` (по умолчанию
`E:\WoW_Forever`); он должен быть отдельной установкой.

Скрипт переместит WTF, Cache и Interface/AddOns тестовой копии в её
`.forever-multi/clean-client-...`, запишет result.json и выведет путь резервной
копии. CASC, `.build.info`, EXE и оригинальный клиент не изменяются.
Там сохраняются и наши AddOns для последующего подключения. После запуска
игры настройки будут созданы заново обычным способом.

1. Создайте **новую** учётную запись на `http://127.0.0.1:8088`.
2. В Multi выйдите из старой сессии и войдите новой учётной записью.
3. Используйте обычные Address `127.0.0.1`, Portal `trinity.actual.battle.net`,
   bnet port `1119` и подготовленную тестовую копию.
4. Нажмите «Играть», дождитесь готовности ключа, затем войдите в игре.
5. Проверьте создание персонажа и вход в мир. Только после этого подключайте
   наши дополнения по одному.

## Управление новым комплектом

```bash
~/WoWForEver-clean/server.sh status
~/WoWForEver-clean/server.sh stop
~/WoWForEver-clean/server.sh start
~/WoWForEver-clean/server.sh restart
```

Обычный docker compose из старого `~/WoWForEver` по-прежнему описывает прежний
комплект; управление новым выполняется через созданный server.sh.
start/stop/restart блокируются до завершения первой инициализации.

## Проверки подготовки

Python-тесты проверяют новый Compose и изоляцию хранилищ, выбор протокола по
EXE, свежие схемы/один realm, порядок переключения, остановку при ошибке до
отключения прежнего сервера и ограничение удаления по владельцу Compose.
Windows PowerShell 5.1 проверяет резервирование настроек/AddOns, неизменность
CASC и оригинала. CI отдельно скачивает и распаковывает штатный TDB с проверкой
SHA-256. Полная компиляция ядра, импорт настоящих баз и вход клиента должны
быть выполнены в пользовательском окружении; облачные тесты не объявляются
готовым развёртыванием на его ПК.
