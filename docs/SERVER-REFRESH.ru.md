# Обновление тестового сервера для клиента 70658

Подготовлено 5 ноября 2026 года. Используется **advocaite/TrinityCore, ветка
forever**, зафиксированная ревизия `b6ae12c227ef00bfe24fdaf16fba28acc61a5b7f`.
Это актуальная найденная ревизия Forever, а не обычный retail TrinityCore.
В ней есть auth-миграции для 70634 и 70658. Наличие записи версии не является
подтверждением входа в игровой мир.

Эта ветка объединяет рабочий ForeverAdvancement/ForeverAscension **1.11.0**
из `feat/forever-ascension` и предыдущие инструменты переноса клиента/CASC
из `codex/forever-client-migration-20261105`. Все три локальных патча и
инъекция модуля проверены на новых исходниках. Проверены Python-тесты и
валидность изолированной Compose-конфигурации. Полная компиляция нового ядра,
обновление настоящих баз и вход в клиент на ПК пользователя ещё не выполнены.

## Что переносится

`scripts/refresh-forever-server.py migrate` сначала собирает отдельный образ.
Исходные сервисы во время компиляции продолжают работать. Затем скрипт:

1. Проверяет, что первичный импорт баз уже завершён. Известный последующий
   сбой `characters.forever_advancement_spells doesn't exist` допускается.
2. Останавливает старые web/bnetserver/worldserver, оставляя старый MySQL.
3. Сохраняет проверяемый gzip-дамп **auth, characters, world и hotfixes**.
4. Создаёт проект **forever-refresh-70658** с собственными MySQL/logs-томами
   и сетью; восстанавливает туда четыре базы.
5. Создаёт пять таблиц `forever_advancement_*`, если их нет, применяет
   привязки заклинаний мода и убирает два старых экспериментальных power-hotfix.
   Существующие строки прогресса не очищаются.
6. Запускает новый сервер и его автоматические SQL-обновления на копии баз.
   Используются штатные порты 1119/8081/8085 и прежний порт сайта.
7. Ждёт сообщений готовности ядра и мода, проверяет из web TCP до
   worldserver:8085 и bnetserver:1119/8081. После этого устанавливает текущий
   ForeverAscension в новую тестовую копию клиента с резервной копией аддона.

Старые контейнеры, базы и `.env` сохраняются. Серверные data, сертификаты,
overrides и downloads используются через прежние пути **только для чтения**.
Поэтому прежние карты и размещённые нами в БД объекты доступны новому серверу;
как на них повлияют upstream-миграции, нужно проверить в игре. Сайт сохраняет
прежний собранный образ. Пустая TDB заново не скачивается и не заменяет наш мир.

Клиент — уже проверенная независимая копия:

```text
E:\WoWForEver-work\experiments\Forever-client-v2\_forever_\Wow.exe
1.60.1.70658, product wowf
```

Исходная новая установка в `E:\WoW_Forever\_forever_` и старый эксперимент
`Forever-Legion-client-v1` сохраняются. Старые CASC/TVFS/root/idx/config/shmem
поверх нового клиента не копируются. Их нужно пересобрать относительно нового
build key; прежние инструменты и отчёты для этого сохранены. Остальные старые
аддоны можно перенести отдельным проверяемым шагом после успешного входа.

## Запуск в WSL

Закройте игру и лаунчер. Нужны Docker Desktop с доступом из WSL, работающий
старый MySQL, Git и Python 3. Для новой сборки, копии базы и дампа нужен
дополнительный запас диска; исходный проект оценивает полный сервер примерно
в 20 ГБ. Полная сборка может идти долго; `--jobs 2` ограничивает параллелизм.

Изолированный каталог исходников позволяет сохранить локальные изменения
старого репозитория:

```bash
cd ~/WoWForEver
git fetch origin codex/server-refresh-70658-20261105 &&
mkdir -p /mnt/e/WoWForEver-work/tools &&
refresh_tools=$(mktemp -d /mnt/e/WoWForEver-work/tools/server-refresh-70658.XXXXXX) &&
git worktree add --detach "$refresh_tools" FETCH_HEAD &&
python3 "$refresh_tools/scripts/refresh-forever-server.py" migrate \
  --old-project "$HOME/WoWForEver" \
  --client /mnt/e/WoWForEver-work/experiments/Forever-client-v2/_forever_ \
  --jobs 2
```

Состояние записывается в
`~/WoWForEver/backups/server-refresh-ДАТА-СУФФИКС/state.json`.
Точный путь печатается **до сборки**, а после успеха выводится
`REFRESH READY`. Сохраняйте этот путь для управления новой копией:

```bash
python3 "$refresh_tools/scripts/refresh-forever-server.py" status --state ПУТЬ/state.json
python3 "$refresh_tools/scripts/refresh-forever-server.py" rollback --state ПУТЬ/state.json
```

После перехода обычный `docker compose` из `~/WoWForEver` управляет **старым**
проектом. Для новой копии используйте команды выше. Снова запускать migrate
при существующем проекте/томах refresh нельзя: скрипт остановится, сохранив их.

При ошибке скрипт останавливает новую копию и запускает прежние контейнеры.
Это возвращает прежнее состояние; если старое ядро падало из-за отсутствующей
таблицы, эта ошибка остаётся в старой базе. Новый том с диагностикой сохраняется.
При ручном rollback прогресс, полученный уже на новом сервере, остаётся в его
отдельном томе и не переписывает прежнюю базу. Ни один том автоматически
не удаляется, `docker compose down -v` здесь не используется.

Все файлы в backups, особенно `compose.private.json`, дампы и конфиги,
содержат приватные настройки или данные аккаунтов. Они создаются с закрытыми
правами, остаются на ПК и не предназначены для загрузки в чат/GitHub.
Для диагностики достаточно строки `Stopped`, стадии и выбранных строк логов.

Варианты с внешним MySQL, общими external-томами/сетями, host networking или
переопределениями DatabaseInfo требуют отдельного переноса: автоматический
режим не должен подключить новое ядро к прежней базе.

## Авторизация после запуска

Запускайте скопированный клиент через **ForeverLauncher.exe 2.0.5**;
Beta нужен только если 2.0.5 не позволяет выбрать эту папку.

В прежнем Connection.log была отдельная причина отказа TLS:
`ERROR_NETWORK_MODULE_SSL_COMMON_NAME_DOES_NOT_MATCH_REMOTE_ENDPOINT (1015)`.
Обновление ядра не меняет имя в сертификате. При прежнем сертификате для
`trinity.actual.battle.net` проверьте в Windows hosts строку:

```text
127.0.0.1 trinity.actual.battle.net
```

И в `WTF/Config.wtf` новой копии (при наличии также в `ForeverLauncher.wtf`):

```text
SET portal "trinity.actual.battle.net:1119"
```

Лаунчер должен сохранять это имя, а не подменять его на `127.0.0.1:1119`.
Проверку сертификата не отключаем. Если после `REFRESH READY` вход не проходит,
сравниваем свежие клиентские Connection.log и логи нового bnetserver.

## Лаунчер использует 127.0.0.1 вместо имени: локальный сертификат

В реальном логе v3 подтверждено `loginPortal="127.0.0.1:1119"` и
`ERROR_NETWORK_MODULE_SSL_COMMON_NAME_DOES_NOT_MATCH_REMOTE_ENDPOINT (1015)`.
Это отказ TLS до проверки аккаунта. Ранее отдельная попытка с EU.actual.battle.net
уходила на внешний 34.90.208.189 и получала 14500; эти два отказа нельзя смешивать.
Правка WTF не стала активной при следующем запуске 2.0.5. При изменении поля
«Свой адрес входа» лаунчер показал общее предупреждение о настройках загрузки.
Причина этой валидации по скриншотам не установлена.

Для локального запуска можно сохранить адрес `127.0.0.1:1119` и выдать существующим
CA новый листовой сертификат с SAN `IP:127.0.0.1`. Это обычная проверка сертификата
для IP, а не отключение TLS. DNS-имена исходного сертификата сохраняются, как и
прежние CA, CA key и серверный private key. Установка нового корневого сертификата
на клиент не нужна, если прежний CA уже установлен и доверен.

```bash
python3 scripts/repair-local-login-cert.py apply \
  --state "$HOME/WoWForEver/backups/server-refresh-20261105-134121-3b67e9/state.json"
```

Скрипт берёт существующий путь к сертификатам из приватной Compose-конфигурации,
проверяет цепочку и соответствие ключа, сохраняет предыдущий публичный сертификат
в закрытом каталоге backups и атомарно заменяет только `forever.cert.pem`.
Затем перезапускает **только bnetserver** и проверяет живое TLS-соединение к его
1119 с `-verify_ip 127.0.0.1 -verify_return_error`. Базы, worldserver и клиентские
ресурсы не изменяются. При ошибке восстанавливает старый сертификат.
После успеха выводит `LOCAL TLS OK` и конкретную команду rollback.

Затем в лаунчере используйте прежний «Свой адрес входа» `127.0.0.1:1119`, выберите
«Свой адрес» в списке миров и проверьте копию v3. Внутреннюю валидацию настроек
загрузки эта серверная правка не меняет. Если предупреждение остаётся с прежними
значениями, нужен журнал самого лаунчера. Если игра отключается, нужен свежий
Connection.log: проверка TLS в OpenSSL ещё не является подтверждением входа WoW.
