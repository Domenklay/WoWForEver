# Переход на новую установку Forever и лаунчер 2.0.5

Исходная папка пользователя после уточнения — **`E:\WoW_Forever\_forever_`**.
Цель для тестов — отдельная **`E:\WoWForEver-work\experiments\Forever-client-v2`**.
Прежняя копия `Forever-Legion-client-v1` сохраняется. Из облачной среды диск E:
недоступен: код миграции подготовлен и проверен на синтетических файлах, но
перенос на ПК пользователя и запуск игры ещё не подтверждены.

Предпочтительный лаунчер — указанный пользователем **`ForeverLauncher.exe`
версии 2.0.5**. Если он не позволяет выбрать скопированный клиент, пользователь
разрешил использовать Forever Launcher Beta. Версия лаунчера сама по себе не
устанавливает номер сборки игры и совместимость с игровым сервером.

## 1. Сделать независимую копию новой установки

Закройте новую и старую игру, оба лаунчера и программы обновления клиента.
Следующие команды выполняются в **WSL Ubuntu** из каталога инструментов,
содержащего `migrate-forever-client.py`:

```bash
python3 scripts/migrate-forever-client.py clone \
  --source /mnt/e/WoW_Forever/_forever_ \
  --output /mnt/e/WoWForEver-work/experiments/Forever-client-v2 \
  --old-client /mnt/e/WoWForEver-work/experiments/Forever-Legion-client-v1
```

Сначала создаётся небольшой JSON `Forever-client-migration-*.json` в
`E:\WoWForEver-work\reports`. В него попадают структура установки, активные
product/build/version, имена EXE, размеры выбранных данных, свободное место,
найденные лаунчеры и названия установленных аддонов. Содержимое WTF, токены,
командные строки процессов и игровые ресурсы в отчёт не выгружаются.

Поддержаны три структуры:

- `_forever_` — папка игры, а `Data` и `.build.info` находятся рядом в
  `E:\WoW_Forever`. Копируются только `.build.info`, `Data` и `_forever_`;
  другие клиенты и содержимое диска не захватываются.
- `_forever_` содержит собственные `Data`, `.build.info` и EXE. Копируется эта
  установка, с исключением журналов и временного кэша.
- Указан корень установки с вложенной `_forever_`; папка игры определяется
  внутри него.

Если активных продуктов несколько, скрипт сохранит отчёт и остановится до
копирования. Нужный продукт задаётся `--product ИМЯ_ИЗ_ОТЧЁТА`. Аналогично при
неоднозначном EXE используется `--executable ИМЯ.exe`. Неизвестная структура не
считается старым клиентом автоматически. Для одного только отчёта вместо
`clone` доступна команда `plan`.

Копия создаётся в соседней папке `Forever-client-v2.partial`. Файлы реально
копируются, без hardlink, и перечитываются с проверкой SHA-256. Требуется место
под выбранную установку и небольшой запас. Изменение исходных файлов в ходе
копирования останавливает завершение. После прерывания та же команда проверит
сохранённые файлы и продолжит копирование. Готовая папка не перезаписывается.

Успех отмечается `NEW BASELINE COPY VERIFIED`. В корне копии появляется
`forever-client-migration.json` с хешами и обнаруженной структурой. Маркер старого
эксперимента `legion-client-copy.json` не создаётся: это не разрешение применять
старый CASC writer к неизвестной сборке.

## 2. Проверить запуск через лаунчер

Откройте установленный `ForeverLauncher.exe` 2.0.5. Скрипт ищет этот EXE в
исходной папке игры и её родителе. При доступном Windows PowerShell он читает
только FileVersion/ProductVersion, не запускает лаунчер. Если EXE лежит в другой
папке, путь и версия в отчёте останутся неизвестными.

Выберите **папку новой копии**, напечатанную в `target_game_windows`, если
интерфейс лаунчера позволяет менять клиент. Конкретное название пункта и формат
настройки 2.0.5 пока не проверены; скрипт не переписывает глобальные настройки
лаунчера и не придумывает аргументы запуска.

Если выбора клиента нет, используйте разрешённый Forever Launcher Beta и
выберите ту же скопированную папку. При непринятом EXE или ошибке запуска нужны
текст ошибки и выбранный путь. Совместимость Beta с новым EXE заранее не
подтверждена; подмена EXE старым файлом не является миграцией.

Проверка новой базовой версии: правильный сервер в списке миров, вход в обычный
мир, движение, бой и один обычный квест. Номер сборки из отчёта нужен для
проверки совместимости протокола с нашим сервером; одним изменением
`CLIENT_BUILD` она не обеспечивается. До этой проверки старый пакет Даларана
не устанавливается и телепортация в тестовую карту не требуется.

## 3. Перенести установленные аддоны после базового теста

Снова закройте игру и лаунчер:

```bash
python3 scripts/migrate-forever-client.py addons \
  --output /mnt/e/WoWForEver-work/experiments/Forever-client-v2
```

Источник по умолчанию — установленная папка AddOns прежней тестовой копии,
включая фактические версии ForeverAscension и библиотек. Код из `main` вместо
установленных аддонов не подставляется. Если актуальный комплект находится
в другой игровой папке, укажите `--addons-source /mnt/e/ПУТЬ_К_ПАПКЕ_С_EXE`.
Для старого источника ожидается `WowB.exe`; целевой EXE берётся из маркера новой
копии и может иметь другое имя.

Перед заменой новая исходная папка AddOns сохраняется в отдельной резервной
папке `E:\WoWForEver-work\backups\new-client-v2-addons-*`. Копирование и резервная
копия проверяются по SHA-256. Аддоны, которые есть только в новой установке,
остаются активными. Папки с совпадающими именами заменяются комплектом старого
источника целиком, чтобы не смешивать файлы разных версий одного аддона.
Это миграция файлов аддонов, а не проверка их API:
совместимость и возможные Lua-ошибки проверяются в игре. Старые WTF и
SavedVariables не перезаписывают настройки новой базовой версии.

Откат этого переноса с закрытой игрой:

```bash
python3 scripts/migrate-forever-client.py restore-addons \
  --output /mnt/e/WoWForEver-work/experiments/Forever-client-v2
```

Перед откатом текущие аддоны тоже сохраняются. Настройки игры, CASC и сервер
при этой операции не меняются.

## 4. Перенести эксперименты под фактическую новую сборку

Ресурсы и журналы старого эксперимента остаются в `Forever-Legion-client-v1`.
Старые `.build.info`, `Data/config`, `Data/data/*.idx`, `shmem` и patched ROOT/TVFS
поверх нового клиента не копируются. Они связаны с прежними build key, ROOT,
encoding и каталогом исходного клиента.

После базового запуска и теста аддонов следующий этап зависит от отчёта:
проверить product/EXE и форматы CASC новой версии; подтвердить чтение штатных
ресурсов; заново подготовить клиентский пакет и откат под её собственные
метаданные; проверить одну текстуру и только затем карту. Старые идентификаторы
операций и результаты зелёной текстуры не объявляются результатами новой версии.

Серверная база, персонажи и контент не клонируются вместе с клиентом. Если оба
клиента подключаются к нашему прежнему серверу, они используют его же состояние.
Обновление серверного ядра и новая серверная геометрия требуют отдельной проверки
совместимости по фактическому номеру сборки, который пока неизвестен.
