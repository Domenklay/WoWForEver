# Пробный запуск сервисов из резервной копии 70658

Предыдущий этап на ПК пользователя уже завершён: копия
`baseline-70658-20261107-003902` проверена, четыре базы восстановлены в отдельный
MySQL. Новый `scripts/test-baseline-services.py` проверяет запуск мира, входа и
сайта с восстановленными ресурсами и сертификатами. На ПК пользователя этот
этап успешно выполнен на исходниках `b282fb2`: `RESTORED SERVICES VERIFIED`.
Проверены реальный восстановленный TrinityCore, online realm/build, три модуля,
TCP/TLS входа и веб-сервис; тестовые ресурсы и приватные распакованные файлы очищены.
Отчёт: `/home/Kayter/WoWForEver-restore-trials/forever-services-check-885b9c3e9bc2/report.json`.
Повторять эту проверку без новых изменений не требуется. Команда ниже сохранена
для будущих проверок. Вход клиента и импорт образов на пустой Docker остаются
отдельными непроверенными этапами.

В Ubuntu/WSL:

```bash
(
set -euo pipefail
cd "$HOME/WoWForEver"
git fetch origin codex/native-cdn-70658-20261106
restore_tools=$(mktemp -d "$HOME/WoWForEver-services-tools.XXXXXX")
git worktree add --detach "$restore_tools" FETCH_HEAD
python3 "$restore_tools/scripts/test-baseline-services.py" \
  --backup /mnt/e/WoWForEver-work/reports/baseline-70658-20261107-003902
)
```

Новая резервная копия и сборка не нужны. Используются точные локальные ID образов,
идентичность которых проверена в `docker-images.tar`. Инструмент не выполняет
`docker load`, загрузку образов из сети или замену текущих тегов. Поэтому этот
прогон проверяет восстановленные сервисы на текущем Docker, но отдельно не
проверяет импорт сохранённых образов на полностью пустой машине.

Что делает проверка:

1. Проверяет исходные размеры/SHA-256 файлов копии и идентичности образов.
2. Проверяет место и распаковывает `server-files.tar.gz` в новый приватный каталог
   `~/WoWForEver-restore-trials/forever-services-check-<id>/fs`. Требуется место
   под ещё одну распакованную копию серверных файлов. Абсолютные пути, ссылки,
   специальные файлы и повторяющиеся имена не извлекаются.
3. Создаёт отдельный MySQL-том, импортирует SQL и сравнивает счётчики/структуру
   с моментом резервирования, проверяет десять таблиц модулей.
4. Создаёт внутреннюю Docker-сеть, подключает только тестовый MySQL и три новых
   сервиса. Портов на хосте нет. Новые случайные пароли применяются только к клону.
   Сайт при запуске обновляет SOAP-учётную запись только в тестовой базе.
5. Запускает мир из сохранённого gameplay-образа, bnetserver из сохранённого
   clean-образа с восстановленным entrypoint, сайт из сохранённого web-образа.
   Ресурсы и сертификаты монтируются из **распакованной копии** только для чтения;
   журналы записываются в отдельные новые тома. Старый controller не исполняется.
6. Проверяет текущий процесс мира: TCP 8085, online realm 70 / build 70658 /
   content set 137 и сообщения готовности всех трёх модулей. Проверяет TCP входа
   1119, TLS REST 8081 с исходным CA и именем `trinity.actual.battle.net`, HTTP
   `/healthz`, `/api/status` и контрольную сумму выдаваемого публичного CA.
7. Удаляет только ресурсы с совпадающими именами и метками этого запуска, затем
   распакованные приватные файлы и временные пароли. Исходный архив сохраняется.

Лимиты: MySQL — 1 CPU/1 ГиБ RAM, worldserver — 2 CPU/6 ГиБ, bnet и сайт — по
2 CPU/1 ГиБ. Они работают одновременно с основным сервером; нагрузка на диск и
память временно вырастет. Ожидание мира — до 10 минут (`--timeout 60..1800`).

Ожидаемый итог:

```text
RESTORED SERVICES VERIFIED: /home/Kayter/WoWForEver-restore-trials/forever-services-check-<id>/report.json
```

Отчёт остаётся в WSL: версии/ID, результат SQL-проверки, отфильтрованные сообщения
модулей, TLS/HTTP-проверки и очистка. Приватный журнал ошибок SQL при неудачном
импорте остаётся рядом; его и архивы не публиковать. Отчёт не включает пароли,
строки аккаунтов, содержимое конфигов или закрытых ключей.

Если процесс/Docker был принудительно завершён и отчёт сообщает `cleanup-needed`:

```bash
python3 scripts/test-baseline-services.py \
  --cleanup-report /home/Kayter/WoWForEver-restore-trials/forever-services-check-<id>/report.json
```

Обычная ошибка старта также приводит к очистке. Команда восстановления очистки
сначала проверяет **все** имена и метки; рабочие Compose-сервисы не выбираются.
Не применять `prune`, `down -v` или удаление рабочих томов для этой проверки.

Даже успешный итог не подтверждает вход игрового клиента, игровой обмен или
полное восстановление на новом компьютере. Для этого нужны отдельный клиентский
профиль/подключение и пробный импорт образов на пустом Docker. В отчёте эти поля
явно остаются `false`; рабочий клиент и лаунчер этот инструмент не меняет.

Автоматический интеграционный тест использует настоящий MySQL, внутреннюю сеть,
сгенерированные TLS-сертификаты и небольшие синтетические TCP/HTTP-сервисы.
Он проверяет оркестрацию/изоляцию/очистку и отказ при остановке мира; это не
эмуляция TrinityCore и не подтверждение запуска приватной копии пользователя.

Проверено в [GitHub Actions 42301993948](https://github.com/Domenklay/WoWForEver/actions/runs/42301993948)
на исходниках `464c9313d2f4a44aae19b08dee41d262714a2d97`: 473 общих теста,
30 условных пропусков, реальный MySQL SQL-roundtrip и интеграционный прогон
сервисных фикстур (успех, TLS, отказ мира, очистка, сохранность исходной базы).
Все три задания завершились успешно. Запуск реального восстановленного TrinityCore
на приватном архиве затем подтверждён пользователем отдельно (отчёт указан выше).
