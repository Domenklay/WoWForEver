# Снимок работающего эталона 70658

7 ноября пользователь создал свежую копию `baseline-70658-20261107-003902` на исходниках `877b877`
и получил `BASELINE BACKUP VERIFIED`. Затем на этой копии прошёл
[тест восстановления четырёх баз](BASELINE-RESTORE.ru.md):
`DATABASE RESTORE VERIFIED`, тестовые контейнер и том очищены.
Также прошёл [запуск восстановленных сервисов](BASELINE-SERVICES-RESTORE.ru.md)
на `b282fb2`: мир/три модуля, вход TCP/TLS, сайт и очистка проверены.
Вход игрового клиента и импорт образов на пустой Docker ещё не проверены.
Прежняя копия `baseline-70658-20261106-231543`, проверенная после `finalize` на `c9d3442`,
остаётся предыдущей опорной точкой. Повторять создание или SQL-тест сейчас не требуется.

`scripts/backup-clean-baseline.py` сохраняет активный сервер с тремя модулями.
Копирование выполняется на ПК пользователя; облачные тесты не создают его снимок.
Инструмент не выполняет восстановление, миграции, сборку или смену профиля.

Закройте WoW. Из нового checkout инструментов в Ubuntu/WSL:

```bash
python3 scripts/backup-clean-baseline.py create \
  --output "/mnt/e/WoWForEver-work/reports/baseline-70658-$(date +%Y%m%d-%H%M%S)"
```

Это кратковременно останавливает worldserver, bnetserver и web для согласованного
снимка. MySQL остаётся запущенным. При ошибке остановки/дампа или Ctrl-C сервисы
запускаются обратно через `finally`. При принудительном завершении процесса или
ошибке запуска остаётся `resume-required.json`; проверьте сервер командой
`~/WoWForEver-clean/server.sh status`, при необходимости выполните `start`.

После снимка баз сервисы запущены; большие архивы ресурсов и образов записываются
при работающем сервере. Нужное место оценивается до остановки. Старые копии не
перезаписываются. Для пути `/mnt/e/...` проверяется подключение Windows-диска E.
На время копирования удерживается общий lock управления сервером.

Состав приватной папки:

- `databases-current.sql.gz`: свежие auth/world/characters/hotfixes после установки;
- `server-files.tar.gz`: активные bind mounts четырёх сервисов, в том числе
  извлечённые ресурсы и сертификаты; текущие state/Compose/server.sh/overrides;
  текущая запись отката; отслеживаемые рабочие файлы checkout контроллера и
  инструмента резервирования. Git worktree pointer не копируется как репозиторий;
- `docker-images.tar`: точные ID образов четырёх работающих сервисов;
- `manifest.json`: версии, пути, ID образов, снимок счётчиков/схемы и SHA-256;
- `RESTORE.ru.txt`: назначение файлов и границы восстановления.

Клиент WoW, сырые MySQL-тома, журналы и вся история старых копий не включаются.
Прежний SQL в текущей записи отката остаётся старым снимком; новый дамп имеет
отдельное имя `databases-current.sql.gz`. Папка содержит пароли и закрытые ключи,
хранится приватно. Для отчёта достаточно финальной строки, сами архивы присылать
или публиковать не нужно.

Перед успешным итогом проверяются SHA-256/размеры, gzip, файловый архив и ID образов
в Docker-архиве. Для классического Docker ID — хеш конфигурации; для containerd
в Docker Desktop — хеш манифеста или OCI-индекса. Проверяется соответствующая
идентичность: точные корни, хеши метаданных, связь с экспортированными конфигурациями
и наличие их слоёв. Одних строк digest в index.json недостаточно.
Итог — `BASELINE BACKUP VERIFIED: <путь>`.

Повторная проверка работает без Docker и без извлечения файлов:

```bash
python3 scripts/backup-clean-baseline.py verify --backup /путь/к/копии
```

## Если старая проверка завершилась `Exported Docker image identities differ`

6 ноября пользователь подтвердил: корневые OCI-digest в архиве точно совпадают
со всеми четырьмя сохранёнными ID. Старый проверяющий код `716662d` сравнивал их
с хешами конфигураций, поэтому ошибочно отказал после готового экспорта.
Сервер уже был запущен обратно, дамп и образы повторять не требуется.

Из обновлённого checkout выполните:

```bash
python3 scripts/backup-clean-baseline.py finalize \
  --backup /mnt/e/WoWForEver-work/reports/baseline-70658-20261106-231543
```

`finalize` проверяет уже записанные размеры/SHA-256 всех четырёх файлов,
gzip/tar и правильные ID образов. Только после успеха сохраняет прежний manifest
в `manifest-before-finalize.json` и отмечает копию завершённой. Исходные контрольные
суммы не пересчитываются в manifest для обхода ошибки. Незавершённый экспорт,
повреждение или `resume-required.json` блокируют завершение. Команда не обращается
к Docker/SQL, не останавливает сервер и не перезаписывает архивы.

Повтор на `61ff871` выявил вторую ошибку: проверка типа конфигурации запускалась
до отделения служебных артефактов. Диагностика пользователя подтвердила четыре
рабочих `application/vnd.oci.image.config.v1+json` и три служебных
`application/vnd.oci.empty.v1+json`. Последний тип разрешён OCI для метаданных;
он не является конфигурацией контейнера. Исправленная проверка применяет ограничения
типа только к экспортированным рабочим конфигурациям. Корневые ID, хеши метаданных,
связь с рабочими конфигурациями и контрольные суммы архивов проверяются по-прежнему.
Для этой ошибки также используется `finalize` той же папки, без нового `create`.

Проверка целостности не означает успешную пробу восстановления. Следующий этап —
восстановление в отдельном окружении с новым MySQL-томом и непересекающимися
портами, без замены рабочего сервера. Клиент и его профиль сохраняются отдельно.
