# Рабочая ветка 70658 и публикация игрового порта

Пользователь подтвердил: clean-сервер `Phase: ready`, pristine core
b4e7b940593f, EXE 70658. Все основные сервисы работают. Переход сервера на
70707 не выполнялся, поэтому откат/импорт базы для возврата к 70658 не нужен.
Все 39 INSTALL-файлов 70707 сохранены отдельно; native FileVersion и
ProductVersion извлечённого EXE подтверждены как 1.60.1.70707.

В присланном `docker compose ps` у worldserver есть только `8085/tcp`,
без `127.0.0.1:8085->8085/tcp`. Это экспонированный внутренний порт, а не
публикация для Windows-клиента. Статус готовности внутри Docker сам по себе
не проверял эту границу. Это установленная проблема публикации; её связь
с конкретным зависанием/обрывом всё ещё проверяется реальным входом.

`scripts/repair-clean-network.py status` проверяет фактические bindings
контейнера и TCP/TLS на стороне WSL-хоста. TLS проверяется с прежним публичным
CA и именем trinity.actual.battle.net; проверка сертификатов не отключается.
`apply` работает только с ready 70658, сохраняет приватную копию Compose,
исправляет только ports worldserver на 127.0.0.1:8085:8085 и пересоздаёт
только worldserver с --no-deps --no-build. Аккаунты, персонажи, MySQL-volume,
сертификат, ядро и версия клиента остаются прежними. Начальный SQL-импорт
не запускается. При отказе восстанавливается точный исходный Compose.
Чужой процесс на порту не останавливается.

```bash
python3 /path/to/current-tools/scripts/repair-clean-network.py status
python3 /path/to/current-tools/scripts/repair-clean-network.py apply
```

Обычное управление: `~/WoWForEver-clean/server.sh status|start|stop|restart`.
Не используйте docker compose из старого ~/WoWForEver для clean-проекта.
Публичные порты остаются на loopback; доступ извне этой командой не открывается.

Журнал ForeverLauncher 2.0.5/2.0.7 подтвердил отдельную проблему полноты:
CHECK_SELECTION оставляет установленную сборку 70658 в режиме Critical,
хотя в UI выбрано All. Проверены только 1991 priority-0 объектов, после чего
остальное стримится. BOOTSTRAP INSTALLED не доказывает полный набор ресурсов.
Игровые файлы должны скачиваться с проверяемых CDN источников, а авторизация
и realm — использовать наш адрес, публичный CA/сертификат и ключ сервера.


## Ошибка Docker при сетевой проверке

Общее сообщение `Command failed: docker compose -p` не устанавливает причину
отказа. Текущий скрипт выводит название операции (`ps`, `config`, `up`, `exec`),
код завершения и ограниченный stderr Docker, удаляя значения паролей из state
и приватного Compose. Развёрнутый Compose и окружение в отчёт не включаются.
Проверка `status` ничего не пересоздаёт. Сначала выполните её новой версией
инструмента. Если `config -q` отклонён, исходный Compose восстанавливается без
перезапуска worldserver; ошибка возврата после неудачного пересоздания тоже
выводится и больше не скрывается.

Не публикуйте содержимое `compose.private.json`, `state.json`, `.env` или
вывод `docker compose config` без `-q`: они содержат пароли.


### Windows сообщает, что 8085 занят

На ПК пользователя контейнер worldserver остался в `Created`; Docker Desktop
сначала сообщал `/forwards/expose ... 500`, затем `Only one usage of each socket
address ... is normally permitted`. Проверка только `-State Listen` не нашла
конфликт. Полный `Get-NetTCPConnection -LocalPort 8085` обнаружил другой игровой
сервер Windows — `mangosd` — с Established/привязанными сокетами на 8085.
Перезапуск Docker Desktop сам по себе этот процесс не устранил.

Проверяйте владельца порта на Windows, а не только контейнеры и WSL. Отдельный
сервер останавливается только после согласования с владельцем; перед остановкой
по PID повторно проверяется имя процесса. После освобождения порта используется
`~/WoWForEver-clean/server.sh start`. В `docker ps` worldserver должен быть Up
с `127.0.0.1:8085->8085/tcp`; `Test-NetConnection 127.0.0.1 -Port 8085` выполняется
на Windows после готовности сервера. Это проверка TCP, а не успешного входа
клиента. Остановка mangosd не требует удаления баз, клиента или сертификатов.
