# Проверка восстановления четырёх баз из эталона

7 ноября пользователь проверил свежий эталон `baseline-70658-20261107-003902`
и успешно восстановил из него четыре базы в отдельном MySQL на исходниках `877b877`.
Получены `BASELINE BACKUP VERIFIED` и `DATABASE RESTORE VERIFIED`.
Счётчики и структура совпали со снимком, проверены десять таблиц модулей;
тестовые контейнер и том удалены. Отчёт:
`/mnt/e/WoWForEver-work/reports/restore-test-20261107-004340-520b852f5c8f/report.json`.
Рабочий сервер возобновлён и прошёл readiness до экспорта больших архивов.
Повторять этот SQL-тест без новых изменений не требуется.

Проверен на настоящем MySQL в [CI 42295336273](https://github.com/Domenklay/WoWForEver/actions/runs/42295336273):
восстановление созданных тестовых четырёх баз, данных модулей и представления,
отказ на ошибочном SQL, очистка и сохранность источника. Этот CI-прогон использует
тестовые данные; результат на приватной копии пользователя подтверждён отдельно выше.

Команда SQL-теста для будущей повторной проверки в Ubuntu/WSL:

```bash
(
set -euo pipefail
cd "$HOME/WoWForEver"
git fetch origin codex/native-cdn-70658-20261106
restore_tools=$(mktemp -d "$HOME/WoWForEver-restore-tools.XXXXXX")
git worktree add --detach "$restore_tools" FETCH_HEAD
python3 "$restore_tools/scripts/test-baseline-restore.py" \
  --backup /mnt/e/WoWForEver-work/reports/baseline-70658-20261107-003902
)
```

Инструмент:

1. Повторно проверяет исходные SHA-256 архивов, gzip/tar и идентичности образов.
2. Берёт точный ID MySQL из снимка и требует, чтобы он был доступен локально.
   Образы не собираются, не скачиваются и не загружаются поверх текущих тегов.
3. Создаёт новый контейнер `forever-baseline-check-<id>` и новый помеченный том.
   У контейнера нет сети, опубликованных портов, bind mounts или общих томов
   с рабочим сервером. Лимиты — одно ядро и 1 ГиБ RAM; события MySQL выключены.
4. Проверяет свободное место в тестовом томе и импортирует четыре базы из
   `databases-current.sql.gz`. Пароль временный; рабочие учётные данные не нужны.
   Для определителей представлений создаются отдельные заблокированные trinity
   учётные записи с правами только на четыре тестовые базы.
5. Сравнивает число аккаунтов/персонажей и хеш структуры со снимком, проверяет
   наличие и число строк десяти таблиц мультикласса и энциклопедии.
6. Удаляет только свои контейнер и том после повторной проверки их меток.
   При ошибке импорта или прерывании также выполняется очистка.

Результат хранится рядом с копией, в новой папке `reports/restore-test-...`:

```text
DATABASE RESTORE VERIFIED: /mnt/e/.../restore-test-.../report.json
```

SQL-импорт и проверка могут занять несколько минут. Числа сравниваются с моментом
создания выбранной копии, а не с уже изменившимся прогрессом работающего сервера.
В report.json нет паролей или строк аккаунтов. При сбое импорта подробный
`mysql-import.private.log` остаётся приватным; для диагностики достаточно итогового
сообщения/кода ошибки и report.json, не всего архива или приватного журнала.

Если Docker/процесс был принудительно завершён и очистка не закончилась:

```bash
python3 scripts/test-baseline-restore.py --cleanup-report /путь/restore-test-.../report.json
```

Эта команда проверяет имя и метки пробных ресурсов; рабочие Compose-контейнеры
и тома через неё удалить нельзя. Конфигурация рабочего сервера, его базы и
клиентские файлы не выбираются как цель операций инструмента.

Сам SQL-тест проверяет восстановление баз. После него пользователь успешно
прошёл [запуск восстановленных сервисов](BASELINE-SERVICES-RESTORE.ru.md):
worldserver/три модуля, bnetserver с исходным TLS, web, ресурсы/сертификаты и очистка.
Вход игрового клиента и импорт сохранённых образов на пустом Docker ещё не проверены;
полное аварийное восстановление всей установки пока не объявляется проверенным.
